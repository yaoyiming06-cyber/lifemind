# LifeMind 审理整合文件夹设计

## 背景

LifeMind 审理会把长文本拆成多篇笔记。这个拆分保留，但不能把所有小笔记直接堆到 `React/基础`、`React/语法` 这类大目录里。一次审理中，如果模型已经识别出一个明确的整合主题，应把同主题的新笔记放进同名文件夹，并在确认写入前展示旧笔记迁移计划。

## 目标

- 复用现有 `sections[].parentId` 表达本批次内部父子关系。
- 复用现有 `relations[].sourceNodeId / targetNodeId` 连接整合主题与既有 Vault 笔记。
- 复用现有 Tauri `moves` 预览、确认和回滚事务。
- 允许同一个大目录下出现多个整合文件夹，例如 `React/基础/数据投放到网页上方法` 与 `React/基础/表单输入状态管理`。
- 不让模型直接拼最终文件路径，最终路径仍由本地编译器生成。

## 本地编译规则

1. 模型生成一个整合主题 section，例如 `数据投放到网页上方法`，placement 指向既有大目录 `React/基础`。
2. 同主题子 section 使用 `parentId` 指向整合主题 section。
3. 本地编译时，如果一个父 section 下至少有两个成员，成员可以是新子笔记，也可以是通过 `包含` 关系连接的既有 Vault 笔记，则启用整合文件夹。
4. 新子笔记路径从 `React / 基础` 改为 `React / 基础 / 数据投放到网页上方法`。
5. 父 section 自身仍写在 `React / 基础`，作为整合主题入口笔记，避免改变现有笔记规范。
6. 既有 Vault 笔记只生成 move 计划，不直接改内容；如果目标路径已存在或源路径异常，则跳过 move 并放入 `uncertain`。

## 安全边界

- 不按“同路径”自动聚合；必须有明确父 section 或 `包含` 关系。
- 不跨根目录移动旧笔记。
- 不覆盖已有目标文件。
- 不改变审理正文纠错、幻觉抑制、DeepSeek tool-call 协议和后端事务逻辑。

## 验证

- 单元测试覆盖同一大目录下多个整合文件夹。
- 单元测试覆盖既有笔记被加入整合文件夹的 move 计划。
- 构建通过后再生成新的 DMG，并用 `hdiutil verify` 校验。
