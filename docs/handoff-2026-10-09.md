## 用户已确认的产品要求

- 内容完整覆盖优先，特别是手写公式、推导和例题。正式 PDF 审理关闭 OCR，使用页面渲染图为主要视觉证据，PDF 文本层作辅助。
- 公式输出为确认过的 LaTeX，由本地编译为 `$...$` 或 `$$...$$`，在 Obsidian 中呈现数学排版。
- 只将 PDF 底层提取的内嵌图片放入知识笔记；图片携带来源页和位置，模型选择插入位置，本地脚本生成引用并写附件。
- PDF 整页渲染图仅供模型审理；原始证据和整页截图不要进入知识笔记。
- PDF 笔记按原页次序编号，如 `1.1`、`1.2`；章节可参考原文第一章、第二章，小知识点由模型划分。
- 同技术栈、同主题的后续审理应接续编号，如 `2.3 → 2.4`；新主题应进入合适的新章节，如 `3.1`。
- 用户要求所有知识笔记至少进入技术栈下的一个二级文件夹，二级文件夹也要编号并体现内容次序，避免笔记堆在技术栈根目录。
- 已授权以后交付新版本时直接替换 `/Applications/LifeMind.app`。此前采用保留旧应用备份后移动替换的方式。
- 用户曾要求清理 Claude Code 撤销改动后的前端残余；处理时以当前文件引用和 Git 差异判断，保留后来确认的前端设计，不能仅凭文件出现过 Claude 就删除。

模型分析协议为 `lifemind.review.v2`，使用 `submit_review_plan` 工具。顶层字段包括 `protocolVersion`、`stackDecisions`、`sections`、`relations`、`corrections`、`uncertain`、`pageCoverage`。模型返回结构分析计划，本地负责最终 Markdown 与文件路径。`sections` 包含正文、placement、formulas 和 imagePlacements 等字段。

当前默认模型名为 `deepseek-flash`，格式为 `deepseek-strict-tools`；实际用户设置可以覆盖默认值。源码默认 `qualityPasses=1`，可配置两轮审理。默认输出上限：初稿/终稿 10000 token，修复 16000 token。两轮质量审理不是 PDF 页面的分批处理。

## 最近一次实际问题与修复

用户粘贴一段“数据处理 / CheXpert 不确定标签处理”的纯文本，连续三次显示“阻止写入”。来源 ID 为 `pasted-1`，诊断模型为 `deepseek-flash`。

原因为纯文本公式被误套用 PDF 校验：`sourcePage` 在工具 schema 中必须为整数，校验又要求公式只能引用 PDF；模型还可能只在公式对象里填 anchor，而正文没有锚点，重试会携带伪造 PDF evidenceId。

当前修复已存在于工作区，并已在 2026-10-08 重新构建、安装：

- 所有文本来源允许公式；工具 schema 的 `sourcePage` 支持 null。
- 非 PDF 公式归一化为 `sourcePage=null`，清除无意义的 evidenceId，兼容旧 schema 返回的伪 PDF 元数据。
- 非 PDF 图片放置仍被拒绝；真实 PDF 保留来源页与证据校验。
- 提示词和 schema 明确每个 `{{formula:<id>}}` 必须在对应正文出现一次，不能只写 formulas.anchor。
- 增加纯文本公式、两轮审理与最终 Markdown 的回归测试。
- 钥匙串读取/保存通过 async + spawn_blocking 执行，避免阻塞调用线程。
